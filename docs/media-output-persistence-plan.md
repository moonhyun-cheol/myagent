## 1. 현재 상태 (2026-10-12 코드 기준)

| 구분 | 현재 동작 | 문제 |
|---|---|---|
| 이미지 (이미지 생성 모드) | 모델 답변 글에서 파일 번호나 base64를 찾아 `outputs/images/<session>/`에 저장 (`core/src/chat/owui-media.ts`) | 응답 안에 따로 담겨 오는 이미지 결과(`image_generation_call` 등)는 처리하지 않음 |

| 영상 (동영상 생성 모드) | OpenRouter `/videos`에 요청하고 완료될 때까지 확인한 뒤 mp4를 `outputs/videos/<session>/`에 저장 (`chat/video-generation.ts`, `chat/modes/video-gen.ts`) | 파일을 저장한 뒤에만 성공으로 답함. 다만 아래 약점이 있음 |

### 영상 쪽 약점

1. 영상 주소를 이미지 목록(`image_urls`)에 섞어 저장하고, 화면은 `.mp4`로 끝나는지만 보고 영상인지 구분함 (`video-gen.ts` 46줄, `ui/workspace/src/store/workspaceStore.ts` 314줄).
2. 받은 파일이 비어 있지 않은지만 확인하고, 형식·크기는 검사하지 않음. 파일 전체를 메모리에 올린 뒤 저장함 (`video-generation.ts` 118~122줄).
3. 다운로드 주소가 다른 곳을 가리켜도 API 키는 보내지 않음. 하지만 사설 IP 차단이나 리다이렉트 제한은 없음 (`video-generation.ts` 112~116줄).
4. 작업 번호(`jobId`)를 저장하지 않음. 15분 제한에 걸리거나, 앱을 재시작하거나, 사용자가 중지하면 비용을 낸 결과를 다시 받을 수 없음 (`video-generation.ts` 74, 91, 104줄).

## 2. P0: 이미지·영상 공통 저장 구조

1. **메시지 저장 형식**
   - 새 필드 `media: [{ kind: 'image' | 'video', url, mime, bytes, sha256 }]`를 추가한다.
   - 화면은 확장자가 아니라 `kind`로 이미지와 영상을 구분한다.
   - 기존 `image_urls`는 예전 대화를 읽을 때 계속 지원한다.
2. **공통 저장 함수**
   - 파일 형식은 내용(파일 시그니처)으로 검사한다. 이미지는 PNG/JPEG/WebP/GIF, 영상은 MP4/WebM만 받는다. HTML 오류 페이지는 거부한다.
   - 크기 상한을 둔다. 영상은 메모리에 올리지 않고 디스크로 바로 받는다.
   - SHA-256으로 중복을 거른다. 임시 파일에 쓴 뒤 이름을 바꿔 저장하고, 기존 경로 보호 규칙을 그대로 적용한다.
3. **이미지 결과 꺼내기 (CQR_PA 계획의 P0)**
   - 완료된 응답(`output[]`)과 스트리밍 이벤트에 담긴 이미지 결과를 모두 꺼낸다. 나뉘어 오는 경우, 중복, 이미지만 있는 경우, 글과 섞인 경우를 지원한다.
   - 로컬 파일로 먼저 저장한 뒤 화면에 넘기고, 대화를 다시 열어도 같은 이미지가 보이게 한다.
   - 처리할 수 없는 종류의 결과는 "성공"이 아니라 "확인 안 됨"으로 표시한다. 일반 대화에서 영상이 바로 오는 경우는 현재 근거가 없으므로 구현하지 않고 이 규칙으로 걸러지게만 한다.
4. **영상 결과 검증 강화**
   - 현재의 "비어 있지 않음" 확인을 공통 저장 함수의 검사로 바꾼다.
5. **성공 판정**
   - "생성 성공"은 실제 파일이 확인됐을 때만 표시한다. 모델이 "만들었습니다"라고 답한 것만으로는 성공이 아니다.

## 3. P1: 복구 가능성과 안전성

1. **영상 작업 번호 보관**: 요청 직후 작업 번호, 확인 주소, 상태를 대화 기록에 남긴다. 시간 초과나 재시작 후 「결과 다시 받기」로 확인·다운로드만 다시 한다. 새로 생성하지 않으므로 추가 비용이 없다.
2. **중지의 의미 표시**: 사용자가 중지하면 앱은 확인만 멈추고, 공급자 쪽 작업과 비용은 계속될 수 있다. 이 점을 화면에 알리고 1번으로 나중에 받을 수 있게 한다.
3. **다운로드 보안 공통화**: https만 허용하고, 리다이렉트 횟수를 제한하고, 사설 IP를 막는다. 다른 곳으로 가는 요청에는 인증 정보를 보내지 않는다. `core/src/browser/url-guard.ts` 재사용을 검토한다(아직 내용 미확인).
4. **복구용 기록**: 이미지는 저장에 실패하면 원본 데이터를 제한된 복구용 기록에 남긴다. 이 기록은 토큰 로그, 일반 대화 기록, 모델에 다시 보내는 내용과 섞지 않는다. 영상은 크기가 크므로 원본은 남기지 않고 작업 번호와 다운로드 정보만 남긴다.
5. **비용 승인**: 다시 생성, 모델 변경, 자동 재시도는 승인을 받는다. 영상은 더 엄격하게 한다.
6. **모델에 다시 보내는 내용**: 영상 파일 자체는 다음 대화 때 보내지 않고 파일 정보만 보낸다. 미리보기 이미지는 `attachments/video-keyframes.ts` 활용을 검토한다(아직 내용 미확인).
7. **출력 설정**: 생성 의도와 모델 능력에 맞춰 명시적으로 관리한다. 일반 대화를 이미지 생성 모드로 바꾸는 것만으로 해결하지 않는다.

## 4. 검증 항목

### 이미지
- 이미지+글, 이미지만, 글만, 나뉘어 오는 스트림, 완료 응답에만 있는 이미지, 다운로드 실패, 중복 결과
- 일반 대화에서 이미지 모델로 실제 생성 → 파일 저장, 화면 표시, 다시 열었을 때 표시
- 저장 실패 시 원본 보존, 일반 글·도구 응답 회귀 없음

### 영상
- 생성 중 앱 재시작 후 결과 다시 받기
- 시간 초과 후 공급자 쪽에서 늦게 완료된 경우
- `failed` / `expired` 상태
- mp4가 아니거나 HTML인 파일, 0바이트, 크기 상한 초과
- 다른 주소로 리다이렉트
- 생성 중 중지
- 대화를 다시 열었을 때 영상 표시
- 예전 대화(`image_urls`에 mp4가 섞인 기록)의 영상 표시

## 6. P1 4~6 반영 내용 (2026-10-13)

- **복구용 기록(4)**: 이미지 저장에 실패하면 원본 base64를 `data/media-recovery/<session>/*.json`에 남긴다. 한 건 약 30MB, 대화당 20건, 14일까지만 보관한다. 대화 기록·토큰 로그·모델 입력과 섞지 않고 자동으로 다시 읽지 않는다. 영상은 원본을 남기지 않는다(작업 번호로 다시 받기).
- **비용 승인(5)**: 이미지 생성 모드에서 첫 요청이 글만 돌려주면 자동으로 한 번 더 요청하던 동작을 없앴다. 그리던 지시문은 첫 요청에 함께 보낸다. 캔버스 이미지 카드의 「재생성」은 확인 창을 거친다. 영상은 자동 재요청이 원래 없고, 결과 다시 받기만 제공한다. 「모델을 바꿔 다시 보내기」 기능은 현재 코드에 없어서 따로 막을 곳이 없다.
- **모델에 다시 보내는 내용(6)**: 다음 대화 때 생성 결과는 `[저장된 생성 결과 · 파일 내용은 보내지 않음: 동영상 video/mp4 3.0MB (파일명)]` 한 줄로만 알린다. 미리보기 이미지(`video-keyframes.ts`)는 대화마다 이미지 입력 비용이 붙고 ffmpeg 처리 시간도 들어서 자동으로 붙이지 않는다. 사용자가 영상을 직접 첨부하면 기존 첨부 경로가 미리보기를 만든다.
