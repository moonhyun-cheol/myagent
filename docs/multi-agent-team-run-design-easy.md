- **원본 문서**: `docs/multi-agent-team-run-design.md` (24차 갱신 기준)
- **현재 진행 상태**: 설계 초안 단계입니다. 여러 AI가 동시에 일하는 '팀 실행' 본체 프로그램은 아직 작성하지 않았으며, 준비 과정에서 발견한 **'작업 되돌리기(원상 복구)' 관련 결함 4건(단계 0 ~ 0-4)만 먼저 수정을 마쳤습니다.**
- **이 문서의 목적**: 개발 용어와 코드 파일 이름 때문에 읽기 어려웠던 원본 보고서의 내용을 **비개발자·의사결정자도 막힘없이 이해할 수 있도록 일상 용어로 풀어 쓴 문서**입니다. 원본의 세부 사실, 예외 상황, 한계점, 검증 내역을 생략하지 않고 모두 담았으며, **「라. 결정해야 할 점」의 번호(1~21번)는 원본 문서와 완전히 같게 맞춰 두었습니다.**

## 가. 오케스트레이션(팀 실행)이 무엇인가

한마디로 **"하나의 프로젝트 업무에 여러 명의 AI 직원이 팀을 이루어 동시에 달라붙어 처리하는 작업 방식"**입니다. 이 문서에서는 이를 **팀 실행**이라고 부릅니다.

### 1. 지금 방식과 무엇이 달라지나?

| 구분 | 지금 방식 (단일 에이전트) | 새로 만들 방식 (팀 실행) |
|---|---|---|
| **일하는 주체** | AI 직원 **1명**이 처음부터 끝까지 혼자 처리 | **총괄 반장 AI 1명(조율 에이전트)** + **실무 담당 AI 여러 명(작업 에이전트)** |
| **진행 방식** | 1번 끝내고 → 2번 하고 → 3번 하는 식의 **한 줄 순서대로 진행** | **공유 업무 현황판(작업판)**을 보고 진행. 먼저 해야 할 일이 끝났고 건드릴 파일이 서로 겹치지 않으면 **여러 업무를 동시에 진행** |
| **사용하는 AI 모델** | 대화방에서 처음에 고른 AI 모델 1개만 계속 사용 | 업무의 난이도·성격(등급)에 따라 **어려운 일은 고성능 모델, 단순한 일은 빠르고 저렴한 모델**로 나누어 배정 가능 |
| **업무 시작 방식** | 사용자의 요청 한 번 | 똑같이 사용자의 요청 한 번으로 시작. 반드시 거창한 '계획 수립(플랜) 모드'를 먼저 거칠 필요가 없으며, 기존 계획서·사용자의 직접 지시·작업 도중 새로 발견된 할 일이 모두 같은 업무 현황판에 올라감 |

### 2. 팀 실행을 움직이는 4가지 핵심 요소

1. **팀 실행기 (현장 관리 시스템 — AI가 아니라 규칙대로 움직이는 프로그램)**
   - 업무 현황판을 관리하고, 실무 AI들을 출근시키고, "지금 이 파일은 다른 AI가 고치는 중이니 만지지 마"라고 파일 사용권을 판정하며, 화면 진행 상황 표시와 사용자 승인 요청을 중간에서 전달합니다. 판단이 흔들리지 않도록 AI가 아니라 정해진 프로그램 코드로 작동합니다.
2. **조율 에이전트 (총괄 반장 AI — 1명)**
   - 사용자의 요청을 받아 세부 업무 항목으로 쪼개어 현황판에 올리고, 실무 AI들이 끝낸 결과물을 검수하고, 막히거나 실패한 업무를 다시 배정하며, 마지막에 전체 프로그램 점검(진단)과 테스트를 직접 실행해 마무리 답변을 작성합니다.
3. **작업 에이전트 (실무 담당 AI — 여러 명)**
   - 현황판에 올라온 세부 업무 **딱 하나씩만** 맡아서 자기 범위의 파일을 읽고 수정한 뒤 결과를 보고하고 퇴근합니다.
4. **작업판 (공유 업무 현황판 — 팀 실행 1번당 기록 파일 1개)**
   - 모든 세부 업무의 목록과 상태를 적어 두는 장부입니다. 각 업무마다 다음 정보가 적힙니다.
     - **업무 번호와 제목·지시 내용**: 무엇을 해야 하는지
     - **현재 상태**: 대기 중 → 배정됨 → 작업 중 → 검수 대기 → 완료 / 실패 / 건너뜀
     - **선행 업무**: 어느 번호의 업무가 먼저 끝나야 시작할 수 있는지
     - **담당 파일 범위**: 이 업무에서 건드려도 되는 파일이나 폴더 구역
     - **난이도 등급**: 어떤 수준의 AI 모델을 배정할지 정하는 기준
     - **완료 기준**: 무엇을 만족해야 끝난 것으로 볼지
     - **담당자 이름표 및 작업 결과 요약**: 누가 맡았고 어떤 파일을 어떻게 고쳤는지
     - **인수인계 메모**: 다음 업무를 맡을 다른 AI가 꼭 알아야 할 결정 사항(예: 새로 정한 이름 규칙, 데이터 형식 등)

### 3. 첫 번째 버전에서 일부러 하지 않는 것 3가지

처음부터 구조를 너무 복잡하게 만들면 안정성이 떨어지므로, 첫 버전에서는 아래 세 가지를 제외합니다.

- **작업자마다 프로젝트 폴더 전체를 따로 복사해 주는 방식(git worktree 격리)**: 용량과 관리 부담이 커서 첫 버전에서는 같은 작업 폴더 안에서 담당 파일 구역을 나누어 쓰는 방식으로 갑니다.
- **프로그램이나 컴퓨터가 갑자기 꺼진 뒤 켰을 때 알아서 이어서 도는 자동 복구**: 비정상 종료 후 자동으로 다시 돌리지는 않고, 저장된 업무 현황판의 기록을 보고 다시 시작하는 방식을 씁니다.
- **사용자가 직접 채팅방을 여러 개 열어 일을 나누어 시키는 방식**: 사용자는 지금처럼 **채팅방 하나에 요청 하나만** 올리면 되고, 그 안에서 팀이 알아서 움직입니다.

### 4. 참고한 외부 기술

- **`oh-my-openagent`**: 업무 간 선후 관계에 따른 동시 실행, 난이도별 모델 배분, 앞선 업무가 실패하면 그 업무에 연결된 후속 업무만 건너뛰기, 총괄 반장만 최종 통합하기 등의 **설계 아이디어**를 참고했습니다. (단, 저작권 라이선스 조건 때문에 프로그램 코드는 한 줄도 가져오지 않고 우리 프로그램에 맞춰 새로 직접 만듭니다.)
- **`openai/symphony`**: 작업별 공간 분리 개념을 참고했습니다.

## 나. 현재 프로그램(MY Agent) 상태 정밀 진단

코드를 구석구석 읽어 본 결과, **기존 프로그램을 다 뜯어고칠 필요 없이 지금 있는 '1인 작업 엔진'을 부품처럼 재사용해 그 위에 팀 관리 시스템을 얹을 수 있다**는 결론이 나왔습니다. 다만 원래 혼자 일하는 전제로 만들어진 부분들이 있어서, 여럿이 동시에 돌 때 충돌하는 지점들을 정확히 찾아 해결책을 세웠습니다.

### 1. 지금 프로그램에서 그대로 활용할 수 있는 장점

- **실무 AI를 쉽게 여러 명 띄울 수 있는 구조**: 현재 AI가 코드를 읽고 고치는 핵심 엔진은 부를 때마다 '어떤 AI 모델을 쓸지, 어느 폴더에서 일할지, 중지 신호와 승인 창을 어디로 연결할지'를 매번 따로 지정받습니다. 즉, 이 엔진을 여러 번 동시에 호출하기만 하면 곧바로 여러 명의 실무 AI가 됩니다.
- **끼워 넣을 자리가 딱 한 군데뿐임**: 대화방에서 작업 엔진을 부르는 길목이 프로그램 전체에서 단 한 곳뿐입니다. 여기저기 고칠 것 없이 그 길목 한 곳에만 '팀 실행 스위치'를 달면 됩니다.
- **중지 버튼 연동**: 사용자가 화면에서 「중지」를 누르면, 총괄 반장 아래에서 일하던 모든 실무 AI들도 즉시 함께 멈추도록 이미 묶여 있습니다.
- **대화방당 작업 1개 제한과 충돌하지 않음**: 현재 프로그램은 한 대화방에서 두 개의 요청을 동시에 못 돌리게 입구를 막아 두었는데, 팀 실행은 '그 요청 1개의 안쪽'에서 여러 AI가 움직이는 방식이라 입구 제한에 걸리지 않습니다.
- **채팅창이 지저분해지지 않음**: 대화방에 최종 답변 말풍선을 저장하는 일은 작업 엔진 바깥에서 처리합니다. 따라서 실무 AI들이 내부에서 아무리 많이 움직여도 채팅 기록에는 총괄 반장 AI가 정리한 최종 답변만 깔끔하게 남습니다.

### 2. 그대로 여럿을 돌리면 깨지는 문제점과 해결책 (코드 정밀 조사 결과)

코드를 20여 차례에 걸쳐 줄 단위로 대조하며 찾아낸 충돌 지점과 각각의 해법입니다.

#### ① AI의 개인 업무 수첩(실행 기록 파일) 덮어쓰기 문제
- **원인**: AI가 일하면서 적어 두는 '할 일 목록, 읽은 파일 표시, 찾아낸 근거 자료, 이어하기 메모'가 **대화방 이름 하나당 파일 하나**에 통째로 저장됩니다. 여러 AI가 같은 대화방 이름으로 동시에 일하면 서로 남의 수첩 위에 자기 내용을 덮어써서 기록이 망가집니다.
- **해결책**: 실무 AI마다 `원래대화방이름__팀실행고유번호_작업자1` 같은 **임시 내부 이름표**를 붙여 주면, 수첩 파일과 자료 폴더가 작업자마다 알아서 따로 만들어집니다.
  - 이름표에 매번 새로운 '팀 실행 고유 번호'를 넣어야, 이전에 끝난 다른 팀 실행의 수첩을 잘못 물려받지 않습니다.
  - 파일 이름이 64글자에서 잘리는 내부 규칙이 있어서, 전체 이름표 길이가 64자를 넘지 않게 짧게 만듭니다.
  - 팀 실행이 끝나면 실무 AI들이 썼던 임시 수첩과 자료 폴더는 깨끗이 지웁니다.

#### ② 명령어 실행창(터미널) 강제 종료 충돌
- **원인**: AI 한 명이 작업을 마칠 때, 자기 대화방 이름으로 돌아가고 있던 명령어 작업들을 자동으로 전부 끄고 나갑니다. 모든 AI가 같은 대화방 이름을 쓰면, **1번 작업자가 먼저 퇴근하면서 아직 일하고 있는 2번 작업자의 명령어까지 강제로 꺼 버립니다.**
- **해결책**: 위 ①번의 이름표 규칙(`원래대화방이름__팀번호_작업자1`)을 쓰면 이 문제도 자연스럽게 풀립니다.
  - `작업자1`이 끝나면 정확히 `…_작업자1_`로 시작하는 자기 명령만 꺼지고, `작업자2`나 `작업자10`의 명령은 건드리지 않습니다.
  - 반대로 맨 마지막에 **총괄 반장 AI(`원래대화방이름`)**가 끝날 때는 그 아래 모든 작업자의 남은 명령까지 한꺼번에 깔끔하게 정리됩니다.
  - 사용자가 화면에서 특정 작업 줄의 「취소」 버튼을 누를 때도 그 작업자의 임시 이름표가 함께 전달되어 해당 명령만 정확히 취소됩니다.

#### ③ 인터넷 브라우저 창 충돌과 캡처 사진 열람 제한
- **현상과 해결책**:
  - 우리 프로그램에는 **사용자 눈에 보이는 브라우저**와 **뒤에서 조용히 도는 보이지 않는 전용 브라우저(격리 브라우저)** 두 가지가 있습니다.
  - 눈에 보이는 브라우저는 한 번에 주인 한 명만 쓸 수 있으므로 **총괄 반장 AI만** 쓰게 하고, 실무 AI들은 무조건 **보이지 않는 개별 브라우저**만 쓰도록 고정합니다. 그러면 실무 AI끼리 웹페이지가 섞이지 않습니다.
  - **주의할 점 1 (메모리)**: 동시에 일하는 실무 AI 수만큼 뒤에서 크롬 계열 브라우저 창이 따로 열릴 수 있어 컴퓨터 메모리를 그만큼 더 씁니다(동시 작업자 수를 제한해야 하는 이유).
  - **주의할 점 2 (캡처 사진 보안 제한)**: 프로그램 보안 규칙상, AI는 '자기 이름표가 붙은 임시 폴더'에 찍힌 브라우저 캡처 사진만 열어볼 수 있습니다. 그래서 **실무 AI가 찍은 임시 캡처 화면을 총괄 반장 AI가 직접 열어보려 하면 보안 규칙에 막혀 거절됩니다.** 반장 AI가 화면 사진을 꼭 확인해야 할 때는 프로젝트 작업 폴더 안에 직접 저장하게 하거나, 화면 눈으로 확인하는 일은 반장 AI가 직접 맡아야 합니다.

#### ④ 사용 요금·토큰 통계 누락 및 '삭제된 대화방' 유령 줄 생성 문제
- **원인**: AI를 부를 때마다 얼마만큼의 글자(토큰)와 비용을 썼는지 가계부에 적힙니다. 그런데 실무 AI들이 각자의 임시 이름표로 가계부에 기록을 남기면 두 가지 문제가 생깁니다.
  1. 사용량 조회 화면이 임시 이름표를 진짜 대화방으로 착각해 찾다가, 대화방 목록에 없으니 **`(삭제된 대화방 · 앞 6글자)`라는 유령 항목을 실무 AI마다 한 줄씩** 만들어 버립니다.
  2. 정작 사용자가 질문한 **원래 대화방과 원래 질문의 사용량 합계에서는 실무 AI들이 쓴 비용이 통째로 빠져 버립니다.**
  3. 답변 말풍선 옆에 적히는 사용량과 화면 아래의 '직전 처리량' 숫자에도 총괄 반장 AI 혼자 쓴 양만 찍힙니다.
- **해결책**:
  - 수첩은 작업자별 임시 이름표로 나누되, **요금 가계부에 적을 때만은 모두 '원래 대화방 이름'으로 통일**해 기록하게 합니다. 그러면 유령 줄이 생기지 않고 대화별·질문별 통계에 정확히 합산됩니다.
  - 작업이 끝날 때(도중에 오류가 나거나 중지되어 끝날 때 포함) 실무 AI들이 쓴 토큰 양과 모델별 계산 비용을 모두 합산해 원래 대화방의 최종 기록에 반영합니다. (서로 가격표가 다른 모델을 섞어 쓸 수 있으므로, 토큰만 뭉뚱그려 한 모델 가격으로 곱하지 않고 각 작업자가 쓴 모델 가격대로 계산한 뒤 더합니다.)
  - 가계부의 '용도 분류' 칸은 현재 5가지(채팅·승인·이미지·영상·임베딩)만 한글 이름과 색상이 지정되어 있어서, 억지로 새 분류 이름을 넣으면 화면에 영문 코드가 회색으로 깨져 나옵니다. 따라서 첫 버전에서는 기존 '채팅' 분류를 그대로 쓰고, 어떤 작업자가 어떤 모델로 얼마를 썼는지는 업무 현황판 결과 칸에 적어 둡니다.

#### ⑤ 같은 파일 동시 수정 충돌과 '반복 실패 안전장치'와의 미묘한 상호작용
- **원인**: 현재 프로그램에는 작업 폴더 위치를 고정하는 장치만 있을 뿐, 두 AI가 같은 파일을 동시에 고치는 것을 막는 잠금장치가 없습니다.
- **해결책**: 팀 실행기가 **파일 점유(사용권) 장치**를 운영합니다. 실무 AI가 파일을 고치기 직전에 담당 구역을 검사해, 다른 실무 AI가 이미 점유 중인 파일이면 수정을 거절합니다.
- **깊이 확인해 찾아낸 미묘한 함정 2가지**:
  1. **어디서 거절할 것인가**: 도구 실행 '바깥 문지기'에서 거절하면 실무 AI가 여러 파일을 동시에 빨리 읽는 기능(병렬 읽기)까지 통째로 꺼져 속도가 느려집니다. 반면 도구 실행 '안쪽'에서 오류 메시지로 거절하면 읽기 속도는 유지되지만, 현재 프로그램의 **'도구 실행 6번 연속 실패 시 강제 중단'** 규칙에 카운트됩니다. 남의 파일을 고집스럽게 6번 연속 건드리는 AI라면 작업을 중단시켜 반장에게 돌려보내는 편이 오히려 바람직하므로 안쪽 거절 방식을 권고합니다.
  2. **자동 훈수 기능의 함정**: 현재 프로그램에는 부분 수정(`edit_file`)이 같은 파일에서 2번 실패하면 3번째부터 *"부분 수정하지 말고 파일 전체 새로 쓰기(`write_file`)로 덮어써라"*라고 AI에게 자동 조언을 붙이는 기능이 있습니다. 남이 점유 중이라 거절된 것인데 이 조언을 들으면 실무 AI가 파일 전체 덮어쓰기를 시도하게 됩니다. 따라서 점유 거절 메시지에는 **"현재 다른 업무가 사용 중이니 다른 도구로도 같은 파일을 다시 시도하지 말라"**는 명확한 지시를 함께 넣어 주어야 합니다.

#### ⑥ 사용자 승인 알림창의 '5분 시간제한 자동 거절' 병목 현상
- **원인**: 파일 삭제나 대용량 수정, 외부 경로 접근 같은 위험한 작업은 화면에 사용자 승인 확인 창을 띄웁니다(단, 작업 폴더 안의 일반 파일 수정·이름 변경은 원래 승인 없이 바로 실행됩니다). 그런데 확인해 보니 두 가지 구조적 문제가 있었습니다.
  1. 화면에 승인 창은 **한 번에 딱 하나만** 뜨고, 동시에 여러 개가 오면 뒤로 줄을 섭니다.
  2. 게다가 **첫 번째 승인 창이 떠서 사용자의 클릭을 기다리는 동안, 화면 프로그램이 통신 통로 읽기를 잠시 멈추는 구조**입니다. 그런데 서버 쪽에서는 승인 요청을 보내자마자 **5분 제한 시간 타이머**가 돌아갑니다. 결국 실무 AI 3명이 동시에 승인을 요청하면, 사용자가 첫 번째 창을 고민하거나 자리를 비운 사이 **두 번째·세 번째 요청은 화면에 얼굴도 비추기 전에 5분이 지나 자동 거절**되어 버립니다.
  3. 자동 승인 검토 AI가 요청의 적절성을 판단할 때도, 세부 업무 지시서가 아니라 '사용자의 맨 처음 질문'과 비교하기 때문에, 반장 AI가 세부 작업을 쪼개어 시킨 일을 자동 검토 AI가 "사용자가 직접 시킨 적 없는 일"이라며 보류하고 사람에게 확인 창을 띄울 가능성이 있습니다.
- **해결책**:
  - 팀 실행기가 승인 요청을 한꺼번에 올려보내지 않고 **한 번에 하나씩만 번호표를 뽑아 올립니다.** 앞선 승인이 끝나야 다음 실무 AI의 승인 타이머가 비로소 시작되므로, 보지도 못하고 시간 초과로 거절되는 일이 사라집니다. 승인 창 제목 앞에는 `[작업자 이름 · 맡은 업무 제목]`을 붙여 사용자가 누구의 요청인지 알 수 있게 합니다.
  - **남아 있는 한계**: 승인 창 하나가 떠 있는 동안 화면이 통신 읽기를 멈추기 때문에, **승인을 기다리지 않고 열심히 일하고 있는 다른 실무 AI들의 진행 상황 글씨가 화면에서 잠시 멈춰 보이게 됩니다**(실제 작업은 뒤에서 정상 진행됨). 이 화면 멈춤 현상은 화면 프로그램을 손대는 3단계에서 해결합니다.

#### ⑦ 작업 걸음 수 한도(100걸음)와 장시간 작업 점검 카드 중복 문제
- **원인**: 현재 AI 하나는 기본 **100걸음**(연장 시 50걸음씩 최대 2번 자동 연장)까지 움직일 수 있고, **30분마다** 진행 상황을 자동 점검하며, **60분이 넘으면 무조건 사용자에게 "계속할까요?" 확인 창**을 띄웁니다. 이때 경과 시간에는 '승인 창 차례를 기다리느라 가만히 서 있던 시간'까지 전부 포함됩니다.
- **해결책**: 만약 실무 AI들에게도 이 연장·시간 점검 기능을 켜 두면, 줄 서서 기다린 시간 때문에 실무 AI마다 30분 점검과 60분 확인 창이 우후죽순 뜨게 됩니다. 따라서 **실무 AI는 연장 없이 딱 100걸음 한도 안에서만 일하게 하고**, 100걸음 안에 못 끝내면 '미완료(실패)'로 반장 AI에게 돌려보내 반장이 업무를 더 잘게 쪼개거나 다시 맡기게 합니다. 전체 팀 실행의 시간·걸음 수 연장은 **총괄 반장 AI 한 명만** 대표로 점검받습니다.

#### ⑧ 프로그램 전체를 잠시 멈추게 하는 '동기 실행' 도구들
- **원인**: 코드 조사를 통해 일부 기능이 실행되는 동안 프로그램의 심장(이벤트 루프) 전체를 잠시 멈춰 세운다는 사실을 확인했습니다. 이 기능이 도는 몇 초~수십 초 동안은 다른 실무 AI들의 작업도, 화면 진행 표시도, 승인 버튼 응답도 잠시 멈칫하게 됩니다(데이터가 깨지지는 않고 순서대로 처리됨).
  - **플러그인 도구 실행**: 끝날 때까지 최대 **60초** 멈춤
  - **외부 공개 GitHub 저장소 이력 조사 도구(`remote_git_inspect`)**: 명령마다 최대 **180초(3분)** 멈춤
  - **검사 도구가 없는 폴더에서 자바스크립트 진단 실행**: 파일당 최대 60초(최대 10개 파일) 멈춤
  - **자바스크립트 파일 수정 직후 자동 문법 검사**: 파일당 최대 **15초** 멈춤
  - **파일 내용 검색 / git 상태 도구**: 최대 **30초** 멈춤
- **해결책**: 시간이 특히 길고 실무 AI가 굳이 쓸 필요가 없는 **플러그인 도구와 외부 저장소 이력 조사 도구는 실무 AI의 도구함에서 아예 뺍니다.** 빌드·진단·테스트도 반장 AI만 마지막에 한 번 돌리게 합니다. 나머지 짧은 멈춤(파일 검색, 문법 검사 등)이 실제 체감 속도에 얼마나 영향을 주는지는 2단계 동시 실행 테스트에서 직접 시간을 재어 확인합니다.

#### ⑨ 그 밖에 빠짐없이 확인해 반영한 세부 연결 고리들
- **사용자의 "절대 건드리지 마" 제약 조건과 대화 핵심 기억**: 원래 대화방 이름에 묶여 저장되므로, 실무 AI가 임시 이름표로는 읽지 못합니다. 팀 실행기가 부모 대화방에서 이 내용을 직접 읽어 모든 실무 AI의 기본 지침서에 넣어 줍니다.
- **사용자가 채팅에 올린 첨부파일·이미지**: 이 역시 원래 대화방 폴더에만 들어 있으므로, 총괄 반장 AI가 문맥이나 파일 경로로 실무 AI에게 건네주도록 설계했습니다.
- **장기 기억 제안 도구·개인 자동화(스케줄러) 등록 도구**: 실무 AI가 쓰면 임시 이름표가 기록에 남거나 엉뚱한 폴더를 가리키므로 실무 AI의 도구함에서 뺍니다.
- **실무 AI 전용 도구 조정 기능 신설**: 조사해 보니 현재 작업 엔진에는 '특정 도구를 빼거나 새 도구를 추가하는 옵션' 자체가 없었습니다. 그래서 1단계 구현 때 **도구 제외 목록**과 **추가 도구(반장 AI용 작업판 도구 4종)** 옵션을 가장 먼저 만듭니다. (플러그인 목록이 중간에 새로 고침될 때도 제외된 도구가 되살아나지 않게 막습니다.)
- **같은 질문 안에서의 자동 재시도 처리**: AI 서버에 일시적 통신 장애가 나면 프로그램이 자동으로 같은 작업을 다시 부릅니다. 이때 팀 실행기가 아무 생각 없이 업무 현황판을 새로 만들어 버리면 **이미 끝낸 업무를 처음부터 두 번 작업**하게 됩니다. 따라서 자동 재시도로 들어왔을 때는 끝나지 않은 기존 현황판을 찾아 이어서 진행하도록 설계했습니다.
- **앱 켠 직후 90초 임시 파일 자동 청소기**: 프로그램을 켜고 딱 90초 뒤에 쓰이지 않는 임시 폴더를 청소하는 기능이 한 번 돕니다. 앱을 켜자마자 90초 안에 팀 실행을 시작하면 작업 중인 실무 AI의 브라우저 임시 파일이 청소될 가능성이 있어 실제 테스트 확인 항목에 넣어 두었습니다.

### 3. 이번 조사 과정에서 미리 발견해 이미 고쳐 둔 것 (작업 되돌리기 결함 4건 수정 완료)

팀 실행에서 여러 AI가 파일을 고치다가 문제가 생겼을 때 **안전하게 원래 상태로 되돌리는 기능(백업 지점 복구)**을 조사하던 중, 기존 프로그램의 되돌리기 기능 자체에 **파일이 사라질 수 있는 심각한 결함**들이 숨어 있는 것을 발견해 팀 실행 구현에 앞서 모두 수정을 마쳤습니다.

#### 배경지식: 왜 화면에 「수정 수락 / 거부」 창이 안 뜨나?
- 조사 과정에서 화면 코드에 '변경 검토 창(수정 전후 비교 및 수락·거부 화면)' 파일이 들어는 있지만, **실제 화면에는 전혀 연결되어 있지 않다**는 사실을 확인했습니다.
- 과거 작업 기록과 제품 설계 원칙 문서(룰북)를 끝까지 추적한 결과, 이것은 실수로 빠뜨린 것이 아니라 **"AI의 파일 수정은 즉시 디스크에 반영하고, 별도의 수락·거부 확인 창은 두지 않으며, 되돌리기는 백업 지점 기능을 통해 처리한다"**는 공식 제품 원칙에 따른 결정이었습니다. (그래서 이번 결함들도 실제 사용자가 화면 버튼을 눌러 겪고 있던 사고는 아니었습니다.)
- 이 원칙에 맞춰, 팀 실행에서도 별도의 수락·거부 창을 띄우지 않고 **총괄 반장 AI가 '작업 되돌리기 도구'를 사용해 복구하는 방식**으로 확정했습니다.

#### 실제로 고치고 검증까지 마친 4가지 수정 내역 (단계 0 ~ 0-4)

1. **단계 0 수정 — 나중에 고친 기존 파일과 대용량 파일이 되돌릴 때 삭제되던 문제 해결**
   - **원래 문제**: AI가 한 번 일할 때 '맨 처음 수정한 파일'만 백업 지점에 복사해 두고, 두 번째 이후에 추가로 고친 기존 파일이나 2MB가 넘는 큰 파일은 백업에 넣지 않았습니다. 그런데 되돌리기를 실행하면 백업 지점에 없는 파일을 무조건 '이번에 새로 만든 파일'로 착각해 **원래 있던 멀쩡한 파일까지 삭제해 버리는 결함**이 있었습니다.
   - **해결**: 파일을 고칠 때마다 같은 백업 지점에 수정 전 원본을 계속 추가 보관하도록 고쳤고, 진짜로 '수정 전에 원래 없었던 파일 목록'을 따로 기록해 그 목록에 있는 새 파일만 지우도록 안전장치를 넣었습니다. 백업하지 못한 대용량 파일은 함부로 지우지 않고 건너뛴 뒤 알려줍니다.

2. **단계 0-2 수정 — 파일 이름을 바꾼 뒤 내용을 고치고 되돌리면 파일이 증발하던 문제 해결**
   - **원래 문제**: 예를 들어 `옛이름.ts`를 `새이름.ts`로 바꾼 뒤 내용을 수정하고 되돌리기를 하면, 변경 목록에 `새이름.ts`만 올라가서 **`새이름.ts`는 삭제되고 `옛이름.ts`는 복구되지 않아 파일이 양쪽 모두에서 영영 사라지는 문제**가 있었습니다.
   - **해결**: 이름 바꾸기 도구와 패치 이동 도구를 쓸 때 **옛 경로와 새 경로 두 개를 모두** 백업 대상과 변경 파일 목록에 빠짐없이 기록하도록 고쳐, 되돌리면 `새이름.ts`는 지워지고 `옛이름.ts`가 원래 내용으로 정확히 돌아오게 했습니다.

3. **단계 0-3 수정 — 이름을 바꾼 파일의 한쪽 이름만 골라 되돌릴 때 사라지거나 두 개로 복제되던 문제 해결**
   - **원래 문제**: 부분 되돌리기로 `새이름.ts`만 되돌리면 파일이 아예 사라지고, `옛이름.ts`만 되돌리면 똑같은 파일이 옛 이름과 새 이름 두 개로 복제되었습니다.
   - **해결**: 백업 지점에 **'옛 이름 ↔ 새 이름' 짝꿍 관계**(여러 번 연속으로 이름을 바꾼 경우도 끝까지 추적)를 기록해 두어, 어느 한쪽만 되돌리기 요청을 받아도 짝꿍 경로까지 자동으로 함께 처리해 원래 파일 하나로 깔끔하게 돌아오도록 고쳤습니다. *(참고: 파일이 아니라 '폴더 자체의 이름 바꾸기'는 백업 구조상 폴더 이름까지 옛 이름으로 되돌려지지는 않으며, 대신 안의 파일 내용이 복구되고 파일이 사라지지는 않습니다.)*

4. **단계 0-4 수정 — AI 전용 '되돌리기 도구' 기능 대폭 보완**
   - **원래 문제**: 그동안 AI가 직접 쓰는 되돌리기 도구(`workspace_rollback`)는 백업해 둔 옛 파일을 덮어쓰기만 할 뿐 **이번에 AI가 새로 만든 파일은 지우지 않고 남겨 두었으며**, 특정 파일만 골라 되돌리는 기능도 없었습니다. 게다가 정작 AI 자신은 방금 만들어진 백업 지점의 고유 번호(`id`)를 전달받지 못해 번호를 알 길이 없었습니다.
   - **해결**:
     - 전체 되돌리기를 하면 **이번 작업에서 새로 만들어진 파일까지 깨끗이 삭제**해 작업 전 상태로 완벽히 돌아가게 했습니다.
     - 원하는 파일 경로만 지정해 **일부 업무만 부분 되돌리기**도 할 수 있게 했습니다.
     - AI가 백업 지점 번호를 모른 채 빈 값으로 도구를 부르면, 아무 파일도 건드리지 않고 **이 대화방의 최근 백업 지점 목록(최신순 5개)을 친절히 알려주어** 번호를 확인한 뒤 되돌릴 수 있게 했습니다. (이 도구는 항상 사용자의 승인 확인을 거쳐 실행됩니다.)

- **검증 수준**: 단순 함수 테스트뿐만 아니라 가짜 AI 서버를 띄워 실제 작업 엔진 전체를 통과시키는 종합 테스트(78개 검증 항목 전부 통과)와 내부 통신 경로 테스트까지 마쳤습니다.

## 다. 어떻게 만들 것인가 (구현 방향과 단계별 계획)

### 1. 팀 실행이 돌아가는 기본 규칙 5가지

1. **동시 출발 조건**: 앞서 끝나야 하는 선행 업무가 모두 '완료'되었고, 담당 파일 구역이 지금 한창 작업 중인 다른 업무와 겹치지 않는 대기 업무들을 골라냅니다.
2. **인원수 제한**: 컴퓨터 부담을 막기 위해 정해진 동시 작업 인원 상한(기본 권고 3명) 안에서만 실무 AI를 동시에 투입합니다.
3. **실패 격리**: 만약 특정 업무 하나가 실패하더라도 팀 전체가 멈추지 않습니다. **그 실패한 업무의 결과물이 꼭 필요한 후속 업무만 '건너뜀' 처리**하고, 상관없는 다른 갈래의 업무들은 끝까지 계속 진행합니다.
4. **반장 검수 필수**: 실무 AI가 자기 일을 다 했다고 끝내면 곧바로 '완료'가 되는 것이 아니라 **'검수 대기'** 상태가 됩니다. 총괄 반장 AI가 결과와 수정 파일을 확인해 통과시켜야 비로소 '완료'가 되며, 미흡하면 메모를 달아 다시 시킵니다.
5. **빌드·테스트는 반장만**: 여러 실무 AI가 한 폴더에서 동시에 프로그램 빌드나 테스트를 돌리면 결과물이 서로 엉키고 깨집니다. 따라서 실무 AI에게는 테스트·진단 도구를 주지 않고, **모든 통합 점검과 테스트는 총괄 반장 AI만** 돌립니다.

### 2. 팀 실행에서의 되돌리기(원상 복구) 운영 방식과 한계

- 팀 실행기는 그 팀 전체를 아우르는 **공통 백업 지점 딱 하나**를 원래 대화방 이름으로 관리합니다.
- 실무 AI들은 각자 따로 백업 지점을 만들지 않고, 파일을 처음 고치거나 새로 만들기 **직전에** 팀 실행기에게 요청해 공통 백업 지점에 원본 상태를 먼저 기록합니다(반드시 기록이 끝난 뒤 파일 수정 시작).
- 되돌리기가 필요할 때는 **현재 일하고 있는 실무 AI가 한 명도 없을 때만** 총괄 반장 AI가 되돌리기 도구를 실행할 수 있습니다(누군가 작업 중일 때 파일을 되돌리면 읽은 내용과 실제 파일이 어긋나기 때문). 팀 전체를 통째로 되돌릴 수도 있고, 실패한 특정 업무가 건드린 파일만 골라 되돌릴 수도 있습니다.
- **알아 두어야 할 구조적 한계**: 백업 지점은 각 파일의 '이번 팀 실행에서 맨 처음 건드리기 전 원본' 하나만 보관합니다. 따라서 만약 **1번 업무가 고친 파일을 이어서 2번 업무가 또 고쳤다면, 2번 업무가 고친 부분만 쏙 빼서 1번 직후 상태로 되돌릴 수는 없고** 팀 실행 맨 처음 상태로만 되돌릴 수 있습니다. 또한 백업은 대화방마다 최근 5개까지만 유지되며, 한 번 되돌린 것을 다시 '되돌리기 취소(앞으로 감기)' 하는 기능은 없습니다.

### 3. 전체 개발 로드맵 (단계 0 ~ 단계 5)

한 번에 다 만들고 터지는 문제를 잡는 대신, 확인 가능한 단위로 쪼개어 단계별로 올립니다.

| 단계 | 핵심 개발 내용 | 현재 상태 |
|---|---|---|
| **0 ~ 0-4** | 작업 되돌리기 결함 3건 수정 + AI 전용 되돌리기 도구(`workspace_rollback`) 보완 | **완료 및 테스트 통과** |
| **단계 1** | **업무 현황판(작업판)과 팀 실행기 기본 뼈대 구축**. 먼저 실무 AI를 **한 번에 1명씩 순서대로** 내보내어 기존 방식과 똑같이 잘 돌아가는지, 사용량 합산·임시 파일 청소·재시도 이어받기가 정확한지 검증 | **파일 단위 상세 설계 완료** (코드 작성 전) |
| **단계 2** | **실무 AI 2명 이상 진짜 동시 실행**. 파일 점유 잠금장치, 팀 공통 백업 지점 연동, 사용자 승인 요청 한 줄 세우기 적용 | 기본 설계 완료 |
| **단계 3** | **화면 표시 및 스위치 연결**. 진행 내역과 승인 창에 '어느 작업자의 활동인지' 이름표 구분 표시, 화면에 팀 실행 켜기/끄기 스위치 추가, 승인 창 대기 중 화면 중계 멈춤 개선 | 기본 설계 완료 |
| **단계 4** | **난이도별 모델 자동 배분 및 예산 상한**. 업무 등급에 따라 다른 AI 모델을 배정하는 설정표와 팀 실행 전체 비용 한도 장치 추가 | 기본 설계 완료 |
| **단계 5** | **실패 복구 고도화 및 중단 후 재시작 다듬기** | 기본 설계 완료 |
| **추후** | 작업자별 독립 복사본 작업실(git worktree) 격리 검토 | 첫 버전 범위 밖 |

### 4. 바로 시작할 「단계 1」의 구체적인 청사진 요약

원본 문서 4.1절에 정리된 단계 1의 실제 제작 계획입니다.

- **하는 일**: 설정에 '팀 실행 켜짐/꺼짐' 항목 추가 → 엔진에 도구 빼기·더하기 통로 개설 → 업무 현황판 저장 기능 제작 → 총괄 반장 AI에게 현황판 관리 도구 4종(`현황판 읽기`, `업무 추가`, `실무자 투입`, `결과 검수`) 부여 → 실무 AI를 1명씩 투입해 결과 받아오기 → 통신 장애 재시도 시 기존 현황판 이어받기 → 토큰 사용량 합산 및 임시 수첩 자동 청소 → 8가지 자동 검증 테스트 작성.
- **실무 AI 도구함에서 빼는 도구들(잠정안 반영)**: 장기 기억 제안, 예약 작업 관리, 대화방 첨부 이미지 직접 열기, 백업 생성·되돌리기 도구, 터미널 명령 실행, 테스트·진단 실행, 외부 저장소 이력 조회, 플러그인 도구, 그리고 커밋·브랜치 변경처럼 프로젝트 전체 버전을 뒤흔드는 git 도구들.
- **참고 사항**: 단계 1은 내부 뼈대가 제대로 맞물리는지 확인하는 단계라 **아직 일반 사용자 화면에 켜는 버튼이 없고, 팀 공통 백업 지점(단계 2)이 연결되기 전이라 반장 AI가 실무 AI의 수정을 되돌릴 수 없는 내부 검증용 단계**입니다. 기존 코드 파일 7개를 조금 손보고 새 파일 4개를 추가하며, 화면 코드는 전혀 건드리지 않습니다.

### 5. 아직 남아 있는 확인 사항 (솔직한 현황 공유)

보고서에서는 확인된 사실과 아직 확인하지 못한 것을 엄격히 구분해 기록하고 있습니다.

- **단계 1 코딩 직전에 코드만 조금 더 읽으면 바로 확인되는 것 (5가지)**
  1. 새로 추가할 '반장 전용 현황판 도구 4종'을 엔진이 읽기 전용 도구로 취급할지, 사용자 승인을 물어볼지 여부
  2. 플러그인 목록을 중간에 새로 고침하는 코드 주변의 정확한 동작 확인
  3. 대화방 작업 코드가 현재 요청이 '실시간 화면 대화(스트림)'인지 구분해 전달받는 가장 깔끔한 방법
  4. 대화방 기본 정책 저장 코드와 기존 정책 자동 테스트 스크립트가 새 설정 항목(`team_run`) 추가 시 수정이 필요한지 확인
  5. 부모 대화방의 사용량 기록을 덮어쓰는 함수의 정확한 호출 위치 재확인
- **코드를 읽는 것만으로는 알 수 없고, 단계 2 이후 실제로 프로그램을 돌려 봐야만 알 수 있는 것들**
  - 임시 이름표를 통한 수첩 분리·명령어 개별 취소·승인 줄 세우기가 실제 동시 실행 상황에서 빈틈없이 맞물리는지 종합 실행 검증
  - 중단되었다가 다시 이어받은 업무에서, 이전 작업자가 반쯤 고쳐 놓은 파일 위에서 새 실무 AI가 작업을 이어갈 때 문제없이 수습하는지 여부
  - 문법 검사나 파일 검색 같은 '잠시 멈춤(동기 실행)' 도구들이 실무 AI 여럿이 동시에 돌 때 실제로 화면을 몇 초나 지연시키는지 체감 시간 측정
  - 앱 실행 후 90초 시점의 임시 파일 자동 청소기가 작업 중인 실무 AI의 화면 캡처 파일에 영향을 주는지 여부
  - 팀 전체가 외부 모델 중계 서비스(OpenRouter)에 같은 대화방 고정 번호를 보낼 때 요금 할인(캐시 적중) 효율이 어떻게 달라지는지 여부
  - 가짜 테스트 서버가 아닌 **실제 AI 모델**이 백업 목록을 조회해 번호를 골라 되돌리기를 요청하고, 사용자가 화면 승인 카드를 눌러 복구하는 전체 과정
  - 폴더 안의 파일을 먼저 고친 뒤 그 폴더의 이름을 바꾸고 되돌렸을 때의 실제 결과 등 희귀 예외 상황
- *(별도 참고)* 기존 자동 검사 도구 중 외부 확장 서버(MCP) 설정 검사 2개가 현재 실패하고 있는데, 조사 결과 제품 고장이 아니라 옛날 방식의 테스트 데이터가 남아 있어 생기는 현상이며 팀 실행과는 무관합니다.

### 라-1. 단계 1 개발을 바로 시작하려면 필요한 결정 (1~9번)

> 1~8번은 앞서 별도 이견이 없으셔서 **추천안(권고)대로 임시 확정해 단계 1 설계서를 작성해 둔 상태**이고, 9번은 설계 과정에서 새로 나와 추천안만 적어 둔 상태입니다. 지금 다른 선택지로 바꾸셔도 설계서의 해당 줄만 고치면 됩니다.

| 번호 | 결정할 사항 | 선택지 | 추천안 (현재 상태) | 비개발자를 위한 쉬운 설명과 추천 이유 |
|---|---|---|---|---|
| **1** | **'팀 실행 켜기' 설정값을 내부 설정의 어디에 둘까?** | ① 기존 작업 모드(`실행/계획/질문/디버그`)의 5번째 모드로 추가<br>② 기존 `실행` 모드 위에 켜고 끄는 **별도 스위치 항목**으로 추가 | **② 별도 스위치 항목 (`team_run`)**<br>*(잠정 확정)* | 기존 작업 모드는 'AI에게 어떤 도구 묶음과 성격을 줄지' 고르는 칸입니다. 팀 실행은 기본 `실행(agent)` 방식 위에서 혼자 일할지 팀으로 일할지만 정하는 것이므로, 별도 스위치로 두는 것이 기존 기능과 꼬이지 않고 깔끔합니다. |
| **2** | **채팅 화면이 아닌 뒷단 자동 경로(예약 자동화 작업, 외부 단순 호출)에서도 팀 실행을 허용할까?** | ① 허용한다<br>② 허용하지 않는다 (실시간 채팅 화면에서만 허용) | **② 허용하지 않는다**<br>*(잠정 확정)* | 조사해 보니 **'개인 자동화(스케줄러 예약 실행)'는 사람 없이 돌기 때문에 모든 위험 작업 승인이 묻지도 않고 자동 통과**됩니다. 여기서 팀 실행을 허용하면 여러 AI가 사람 확인도 없이 동시에 파일을 지우거나 고칠 수 있어 위험합니다. 첫 버전은 사람이 지켜보는 채팅 화면에서만 허용하는 것을 권합니다(대신 예약 작업에서는 팀 실행을 못 씁니다). |
| **3** | **실무 AI에게 명령어 실행창(터미널) 사용 권한을 줄까?** | ① 준다<br>② 읽기 성격 명령만 준다<br>③ 아예 안 준다 (반장 AI만 사용) | **③ 아예 안 준다 (뺀다)**<br>*(잠정 확정)* | 실무 AI가 명령어 창으로 직접 파일을 만들거나 고쳐 버리면, **팀 실행기의 파일 잠금 검사도 피해 가고 변경 목록과 백업 지점에도 전혀 기록되지 않아 되돌릴 수가 없습니다.** 안전을 위해 첫 버전에서는 실무 AI에게서 빼고 반장 AI만 쓰게 하는 것이 좋습니다. |
| **4** | **실무 AI에게 '플러그인 도구'와 '외부 GitHub 저장소 이력 조사 도구'를 줄까?** | ① 준다<br>② 안 준다 (반장 AI만 사용) | **② 안 준다 (뺀다)**<br>*(잠정 확정)* | 두 도구는 한 번 실행되면 끝날 때까지(최대 1분~3분) **프로그램 전체를 얼려서 다른 실무 AI들과 화면 표시까지 다 멈추게 합니다.** 꼭 필요하면 반장 AI가 쓰면 되므로 실무 AI에서는 빼는 것을 권합니다. |
| **5** | **실무 AI의 내부 대화 맥락 상태를 데이터베이스에 따로 저장할까?** | ① 저장한다<br>② 저장하지 않는다 (메모리에서만 쓰고 버림) | **② 저장하지 않는다**<br>*(잠정 확정)* | 실무 AI는 짧은 단위 업무 하나만 끝내고 퇴근하는 일회성 담당자입니다. 상태를 저장하게 하면 팀 실행을 할 때마다 데이터베이스에 찌꺼기 줄이 계속 쌓여 매번 청소 코드를 돌려야 하므로, 첫 버전은 저장 없이 가볍게 돌리는 편이 훨씬 단순하고 안전합니다. |
| **6** | **작업 도중 새로운 할 일이 발견됐을 때 누가 업무 현황판에 항목을 추가할까?** | ① 실무 AI도 직접 현황판에 추가<br>② **총괄 반장 AI만 추가** (실무 AI는 결과 보고서에 건의만 함) | **② 총괄 반장 AI만 추가**<br>*(잠정 확정)* | 실무 AI들이 각자 현황판에 새 업무를 마구 늘리기 시작하면 작업 범위가 겹치거나 끝없이 일이 불어날 수 있습니다. 실무 AI는 "이런 추가 작업이 필요합니다"라고 보고만 하고, 전체 그림을 보는 반장 AI만 현황판에 정식 등록하는 것이 질서가 잡힙니다. |
| **7** | **실무 AI가 위험한 작업을 할 때 뜨는 승인 요청을 누가 받을까?** | ① **사용자에게 바로 승인 창을 띄운다**<br>② 총괄 반장 AI가 먼저 1차로 걸러 본다 | **① 사용자에게 바로 띄운다**<br>*(잠정 확정)* | 기존 안전 원칙대로 사람(또는 사용자가 켜 둔 자동 승인 정책)이 직접 결정하게 하되, 승인 창 설명에 `[어느 실무 AI가 · 무슨 업무 중 요청했는지]` 꼬리표를 달아 한 번에 하나씩 차례대로 보여주는 방식입니다. |
| **8** | **채팅창 하단에 표시되는 '직전 처리량(토큰 수)' 숫자를 어떻게 보여줄까?** | ① **팀 전체(반장 + 모든 실무 AI) 합산량** 표시<br>② 총괄 반장 AI 혼자 쓴 양만 표시 | **① 팀 전체 합산량**<br>*(잠정 확정)* | 실제로 이번 질문 한 번을 처리하느라 소비된 전체 양을 투명하게 보여주는 편이 맞습니다. (다만 이 숫자를 '반장 AI 한 명의 현재 기억 용량'으로 오해할 여지만 알고 계시면 됩니다.) |
| **9** | **실무 AI에게서 프로젝트 버전 관리(git 커밋·원격 전송·브랜치 전환·강제 복구 등) 도구를 뺄까?** | ① 준다<br>② **안 준다 (반장 AI만 사용)** | **② 안 준다 (뺀다)**<br>*(미확정 — 확인 필요)* | 실무 AI 한 명이 자기 일 끝났다고 마음대로 버전 저장(커밋)을 하거나 작업 갈래(브랜치)를 바꿔 버리면, **옆에서 다른 파일을 한창 고치고 있던 다른 실무 AI의 작업물까지 통째로 같이 묶이거나 날아갑니다.** 조회용 도구를 제외한 상태 변경용 git 도구는 반장 AI만 쓰게 빼는 것을 강력히 권합니다. |

### 라-2. 단계 2(동시 실행)에 들어가기 전에 필요한 결정 (10~14번)

| 번호 | 결정할 사항 | 선택지 | 추천안 | 비개발자를 위한 쉬운 설명과 추천 이유 |
|---|---|---|---|---|
| **10** | **동시에 일할 수 있는 실무 AI의 최대 인원수 기본값을 몇 명으로 할까?** | 숫자 지정 (예: 2명, 3명, 4명…) | **3명**<br>*(잠정 값)* | 인원이 너무 많으면 뒤에서 열리는 브라우저 창 수와 동시 AI 호출 비용·문법 검사 멈춤이 함께 늘어납니다. 아직 실제 속도 측정 전이라 우선 무난한 **3명**을 기본값으로 잡아 두었습니다. |
| **11** | **남이 쓰고 있는 파일을 실무 AI가 건드리려 할 때 어느 단계에서 막을까?** | ① 도구 실행 전 '바깥 문지기'에서 차단<br>② **도구 실행 '안쪽'에서 오류 안내로 거절** | **② 도구 실행 안쪽**<br>*(잠정 값)* | ①번으로 막으면 실무 AI가 여러 파일을 동시에 빠르게 읽는 기능까지 꺼져 작업이 느려집니다. ②번으로 막으면 읽기 속도가 그대로 유지되고, 경고를 무시하고 남의 파일을 6번 연속 건드리는 고집불통 AI를 자동으로 퇴근(실패 처리)시킬 수 있어 유리합니다. |
| **12** | **용량이 너무 커서(2MB 초과 등) 사전 백업에 실패한 파일은 팀 실행 중 수정을 아예 막을까?** | ① 백업 안 됐어도 수정은 허용한다<br>② **백업에 실패한 파일은 수정을 거부한다** | *별도 추천 없음 (선택 필요)* | **① 허용 시**: 대용량 데이터 파일도 AI가 고칠 수는 있지만, 나중에 문제가 생겨 '되돌리기'를 해도 **그 큰 파일만은 옛날 상태로 복구되지 않고 바뀐 채로 남습니다.**<br>**② 거부 시**: 복구 불가능한 변경을 원천 차단해 안전하지만, 2MB가 넘는 파일은 실무 AI가 고치지 못합니다. 안전성과 편의성 중 어느 쪽을 우선할지 정해주시면 됩니다. |
| **13** | **실무 AI가 '폴더 자체의 이름 바꾸기'를 하는 것을 막을까?** | ① 허용한다<br>② **거부한다 (못 바꾸게 막음)** | **② 거부한다** | 앞서 확인했듯 폴더 이름 변경은 되돌리기로 폴더 이름이 자동 복구되지 않는 데다, 폴더 하나 이름을 바꾸면 그 폴더 안에서 일하던 다른 실무 AI들의 파일 경로가 한꺼번에 다 깨집니다. 첫 버전에서는 막아 두는 것이 안전합니다. |
| **14** | **실무 AI가 인터넷 창을 띄워 찍은 화면 캡처 사진을 총괄 반장 AI가 눈으로 확인해야 할 때는 어떻게 할까?** | ① 필요한 캡처는 임시 폴더가 아니라 **작업 폴더 안에 지정해 저장**하게 한다<br>② **화면 확인이 필요한 업무는 애초에 총괄 반장 AI가 직접** 맡는다 | *별도 추천 없음 (선택 필요)* | 보안 규칙 때문에 반장 AI는 실무 AI의 개인 임시 폴더에 있는 사진을 열지 못합니다. 작업 폴더 안에 사진 파일이 생기는 것을 감수하고 ①번으로 갈지, 아니면 코딩은 실무 AI가 하고 최종 브라우저 화면 눈으로 확인하기는 반장 AI가 직접 하게(②번) 역할 분담을 할지 정하면 됩니다. |

### 라-3. 단계 3(화면 연결) 이후 또는 제품 정책 차원의 결정 (15~18번)

| 번호 | 결정할 사항 | 선택지 | 추천안 | 비개발자를 위한 쉬운 설명과 추천 이유 |

### [참고] 이미 확정되어 흔들리지 않는 전제 3가지

1. **즉시 반영 + 도구 기반 복구**: 파일 수정 후 일일이 사람에게 수락/거부 창을 띄우지 않고 바로 반영하며, 복구는 AI의 되돌리기 도구를 통해 안전하게 처리합니다.
2. **자유로운 출발점**: 플랜(계획) 모드를 거치지 않고 일반 대화 요청에서도 곧바로 팀 실행을 켤 수 있습니다.
3. **단일 대화방 경험**: 사용자가 채팅방을 여러 개 열어 관리할 필요 없이, 하나의 채팅 요청 안에서 팀이 움직이고 하나의 종합 답변으로 결과를 받습니다.
