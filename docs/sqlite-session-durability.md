# SQLite 대화 저장 안정성 — 1차

## 범위

대화 저장 계층과 실행 수명주기의 안정성 개선이다. 검색/FTS, 화면 가상화, 과거 결정 검색, 외부 DB 연결, 백업 관리 UI는 포함하지 않는다. 정상 대화에 상시 DB 상태 바를 추가하지 않는다.

## 진행 중 초안과 복구

- DB 스키마는 `user_version = 2`. `assistant_drafts`는 세션/실행 ID별 초안을 보관하며, 사용자 메시지 추가와 빈 초안 생성은 하나의 트랜잭션으로 커밋한다.
- 스트리밍 본문과 공개 작업 로그는 약 1초 간격으로 저장한다. 마지막 토큰 뒤에 이벤트가 없어도 예약된 저장이 수행된다. 도구 활동 스냅샷은 수신 시 즉시 저장한다.
- 본문은 기존 실행 중 버퍼와 동일하게 마지막 200,000자를 보관한다. 공개 작업 로그는 200,000자, 도구 활동은 기존의 최대 40개/개별 출력 제한을 따른다. 숨겨진 모델 내부 추론은 저장 대상이 아니다.
- 미완성 초안은 메시지 목록/모델 문맥에 노출하지 않는다. 정상 assistant 메시지 추가와 해당 초안 삭제는 원자적으로 처리한다.
- 정상 중지 시 기존 중지 처리로 저장한다. 최종 답변 없이 종료되거나 실패한 실행은 남은 초안을 중단 기록으로 확정한다. 저장에 실패하면 초안은 트랜잭션으로 보존되고 오류가 전파된다. 종료 처리 실패로 채팅 실행 잠금이 영구히 남지 않는다.
- 시작 시 소유 프로세스가 종료된 초안만 복구한다. 활성 소유 프로세스의 초안은 건드리지 않는다. 복구 메시지 추가와 초안 삭제는 한 트랜잭션이다. 반복 시작, 삭제, 되돌리기로 중복 응답이 생성되지 않는다.
- 복구 메시지는 `status: stopped`, `model_exclude: true`이며 실패 안내를 포함한다. 미완성 체인 재사용을 막기 위해 해당 세션의 provider continuation 상태를 초기화한다.
- 복구된 도구 활동 중 `running`은 실행 기록 중단 상태(`cancelled`)로 정리하고 실제 결과를 따로 확인하라는 안내를 붙인다. **실제 외부 작업이 취소/롤백되었다는 증거는 아니다.** 도구나 사용자 요청을 자동 재실행하지 않는다.

### 한계

- 강제 종료 직전 아직 커밋되지 않은 내용은 손실될 수 있다. 1초는 타이머 목표이며 이벤트 루프 정체/저장장치 장애 때의 보장이 아니다.
- 소유자 판정은 PID 생존 여부를 보수적으로 확인한다. 접근 거부 또는 PID 재사용으로 생존 여부가 불명확하면 자동 복구를 건너뛴다. 실행이 끝난 뒤 디스크 오류로 남은 동일 프로세스 초안은 재시작 후 복구 대상이 된다.
- 초안은 출력 복구 수단이다. 도구 side effect의 exactly-once 보장, 자동 작업 재개, 완료되지 않은 요청의 재실행 방지용 영구 admission ledger는 아니다.

## 백업 정책

저장소 초기화 시 실행한다. 계속 실행 중인 프로세스에서 자정마다 백업하는 스케줄러는 아니다.

- 위치: 실제 세션 저장 디렉터리의 `backups/`.
- 일일: UTC 날짜 기준 `sessions-daily-YYYY-MM-DD.sqlite`, 같은 날 이미 있으면 추가 생성하지 않는다. 검증된 새 백업 생성 후 최근 7개를 남긴다.
- 스키마 변경 전: `sessions-before-v1-to-v2-<uuid>.sqlite`. 이 백업은 일일 회전에서 삭제하지 않는다.
- SQLite `VACUUM INTO`로 WAL의 커밋된 변경을 포함한 일관된 스냅샷을 만든다. 임시 파일에 생성하고 `PRAGMA quick_check` 성공 후 최종 이름으로 변경한다.
- 스키마 변경 전 백업에 실패하면 변경하지 않는다. 일일 백업 오류도 시작 시 숨기지 않고 전파한다. 디스크 공간/권한을 복구해야 시작할 수 있다.
- **DB 기록만 백업한다. 첨부 원본·이미지·프로젝트 파일은 별도 백업 대상이다.** 백업에는 대화와 private provider continuation 등 민감한 내용이 포함될 수 있다. 원본 DB와 동일하게 접근을 제한해야 한다.
- 삭제한 대화가 이전 백업에는 남을 수 있다. 영구 삭제 요구가 있으면 관련 백업과 별도 첨부 백업까지 보존 정책을 확인해야 한다.

## 오프라인 복원

자동으로 정상 DB를 과거 백업으로 덮어쓰지 않는다.

1. 프로그램과 해당 데이터 폴더를 사용하는 모든 Core 프로세스를 완전히 종료한다.
2. 현재 세션 디렉터리 전체를 다른 안전한 위치로 복사해 복구 전 상태를 보존한다.
3. 현재 `sessions.sqlite`, `sessions.sqlite-wal`, `sessions.sqlite-shm`이 있으면 **함께 별도 위치로 이동**한다. 이전 WAL을 복원할 DB와 섞지 않는다.
4. 선택한 백업을 세션 디렉터리의 `sessions.sqlite`로 복사한다. 해당 스키마를 지원하는 프로그램으로 시작한다. v1 백업은 v2로 이관된다.
5. 대화 내용과 첨부 파일을 확인한다. DB 백업만으로 삭제된 첨부 원본을 되살릴 수는 없다.

기존 JSON은 이관 당시 보존본이지 최신 기록이 아니다. 손상 JSON을 조용히 무시하지 않는 기존 fail-closed 정책은 유지한다.

## 검증

`npm run verify:session-durability`

Core TypeScript 컴파일 후 아래 세 테스트를 실행한다. 모두 분리된 임시 데이터 디렉터리를 사용한다.

- `tools/verify-session-durability.mjs`: 실제 자식 프로세스 강제 종료, idle 구간 마지막 토큰 저장, 공개 로그/도구 복구, 살아 있는 소유자 보호, 정상/중지/실패, 트랜잭션 실패 주입, 삭제/undo, WAL 스냅샷, 백업 중복 방지/보존 개수, 실제 백업 복원, 스키마 변경 전 백업 실패.
- `tools/verify-session-sqlite.mjs`: 기존 JSON 이관/보존, 페이지 조회, 대화 설정/첨부 참조, 3,000 메시지, 삭제와 GC, 손상 JSON/미래 스키마 거부 회귀.
- `tools/verify-chat-run-race.mjs`: 실제 HTTP 연결 중단, 취소 경쟁, 늦은 쓰기 차단 및 다음 실행 중복 방지.

UI 화면 검증과 전체 배포 빌드/업데이트 게시를 대신하지 않는다.
