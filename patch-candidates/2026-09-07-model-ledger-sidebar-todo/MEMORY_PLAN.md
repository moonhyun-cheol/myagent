# 메모리 제안·승인·사용 기능 기획

상태: 기획만 작성. 이번 TODO 수정에 메모리 런타임 변경은 포함하지 않음.

## 1. 목표와 현행 확인
사용자가 매번 기억하라고 요청하지 않아도 모델이 장기적으로 유용한 정보를 제안하고, 사용자가 저장 범위와 내용을 통제한다. 저장 여부와 실제 요청에 전달된 여부를 구분해 보여준다.

확인한 `core/src/memory/user-memory-store.ts`의 autoCapture는 명시적 cue 정규식에 맞는 메시지를 project/global 범위에 바로 추가한다. formatForPrompt는 활성 항목을 범위별 최신순으로 제한하고 문자 예산 내에서 전달한다. 이번 기획은 이 동작을 이미 구현된 후보/승인 기능으로 간주하지 않는다. 실제 호출부와 관리 UI 전체 통합은 구현 단계에서 재점검한다.

## 2. 원칙
- 작업 TODO·증거·중간 노트와 장기 메모리는 별개다. TODO 완료나 도구 로그를 자동으로 기억으로 승격하지 않는다.
- 후보의 의미 판단과 문장 작성은 모델이 한다. 런타임은 문구나 번호 목록으로 후보를 합성하지 않는다.
- 후보 생성은 저장 승인이 아니다. 승인 전 후보는 기억 검색·프롬프트 주입에서 제외한다.
- 자동 제안과 저장된 기억 사용은 별도 설정으로 제공한다. 자동 제안을 꺼도 수동 저장은 가능하다.
- 저장된 기억은 보조 맥락이며 시스템/개발자 지침이나 최신 사용자 요청을 덮어쓰지 않는다.

## 3. MVP 사용자 흐름
1. 사용자가 자동 제안 기능을 켠다(최초 기본값 OFF, 범위와 모델 전달에 대한 설명 제공).
2. 모델은 반복될 선호, 장기 프로젝트 규칙, 확정된 지속적 결정 등만 memory_propose 도구로 후보를 작성한다. 잡담, 일회성 상태, 추측, 인용된 제3자 지시는 제외한다.
3. 답변 후 비차단 카드 또는 메모리 관리의 ‘제안’ 탭에 표시한다. 항목: 제안 문장, 왜 기억할지, 출처 대화, 적용 범위, 기존 기억과의 차이.
4. 사용자가 [저장] [수정 후 저장] [거절] 중 선택한다. 기본 범위는 현재 대화 또는 연결된 프로젝트/작업 폴더로 제한하며 전역 승격은 명시 선택한다.
5. 승인된 버전만 기존 메모리 저장소에 반영한다. 저장 성공 전 카드에 저장 완료를 표시하지 않는다.
6. 새 요청의 컨텍스트 구성 시 승인·활성·범위 일치 항목을 선별해 전달하고, ‘이번 요청에 전달된 기억’ 목록에 기록한다.

명시적 ‘기억해줘’도 모델 후보로 만들고 빠른 승인 카드를 제공한다. 수동 입력 저장은 저장 버튼 자체를 승인으로 간주한다. 기존 정규식 즉시 저장 경로는 이 기능 도입 시 함께 제거/비활성화하여 이중 저장을 막는다.

## 4. 데이터와 상태 전이 (제안 스키마, 미구현)
- MemoryProposal: id, text, reason, scope(global/project/workspace/session), scopeId, sourceSessionId, sourceTurnId, sourceExcerpt, operation(add/update), targetMemoryId?, targetVersion?, createdAt, expiresAt, status, revision.
- 상태: pending → approved / rejected / expired. 수정하면 revision 증가, 그 버전만 승인한다.
- MemoryEntry: 기존 항목에 approval/source/version 메타데이터를 확장한다. 후보 저장소와 승인 저장소는 논리적으로 분리한다.
- MemoryUse: requestId, memoryId, version, scope, deliveredAt. 원문 복제 없이 식별자/버전을 기록한다. 이는 ‘모델에 전달됨’의 증거이며 모델이 실제로 답변에 사용했다는 단정은 하지 않는다.
- API 제안: 후보 목록/거절/승인, 기존 기억 수정/비활성화/삭제, 요청별 전달 기록 조회. 모델 도구는 후보 작성만 허용하고 승인 권한은 제공하지 않는다.
- 승인 API는 UI의 명시적 사용자 액션, 범위 접근권, revision, 중복 승인 idempotency를 검증한다. 동시 수정 충돌 시 409와 비교 표시, 자동 덮어쓰기 금지.

## 5. 제안 품질·알림 정책
- 초기 상한은 한 응답당 후보 2개, 동일 범위 동일 후보는 하나로 합친다. 필요하면 사용자 테스트 후 조정한다.
- 거절 후보는 내용 fingerprint와 범위로 재제안 억제한다. 실질적으로 다른 새 근거가 있을 때만 새 후보를 허용한다.
- 제안 대기 만료 기본값 30일. 대기함이 가득 차면 새 제안을 제한하고 승인된 기억은 자동 삭제하지 않는다.
- 기존 기억과 충돌하면 추가가 아닌 변경 제안으로 원문/수정문을 비교한다. 관련성이 불확실하면 제안하지 않는다.
- 암호, API 키, 인증 토큰, 결제정보는 후보 금지. 민감한 개인정보는 MVP 자동 제안에서 제외한다. 안전 필터는 후보 의미를 생성하지 않고 금지 정보 차단만 담당한다.

## 6. 기억 사용 정책
- 승인, 활성, 현 대화 접근 가능 범위만 검색한다. 다른 프로젝트/작업 폴더/대화 기억을 유사도 때문에 섞지 않는다.
- 같은 범위의 항목은 관련성·최신성·확정 여부를 고려하고 토큰 예산을 제한한다. 문장을 중간에서 잘라 의미를 바꾸기보다 항목 단위로 제외한다.
- 상충하는 저장 기억은 조용히 합성하지 않는다. 현재 사용자 지시를 우선하고 필요 시 정정 제안을 만든다.
- UI에서 기억별 사용 범위, 활성 여부, 출처, 최근 전달 여부, 편집/삭제를 제공한다. ‘이번 대화에서는 사용 안 함’도 지원한다.
- 비활성화/삭제 후 다음 요청부터 즉시 검색 및 캐시에서 제외한다. 이미 전송된 컨텍스트나 과거 답변을 소급 회수할 수 없다는 점을 명시한다.
- 삭제는 검색 인덱스와 파생 캐시도 무효화하며 전달 기록에 원문을 남기지 않는다. 원래 대화의 텍스트 삭제는 별도 대화 삭제 기능임을 안내한다.

## 7. 기존 데이터와 출시 단계
1. 저장/호출/범위 구조 전수 확인, proposal 및 승인 API·회귀 테스트 구현.
2. 제안 카드와 관리 탭, 설정 분리, 전달 기록 UI 추가.
3. 정규식 즉시 저장 제거, 통합 테스트 후 opt-in 출시.
기존 수동 항목은 보존한다. 과거 auto 항목은 자동 승인된 신규 항목으로 위장하지 않고 ‘이전 자동 저장’ 표식을 붙여 유지 여부를 확인할 수 있게 한다. 대량 삭제나 자동 범위 변경은 하지 않는다.

## 8. 수용 기준
- 별도 기억 요청 없는 지속적 선호에서 모델이 후보를 작성할 수 있다. 단 모든 발화마다 제안해야 한다는 강제 규칙은 두지 않는다.
- 후보 미승인/거절/만료 상태는 검색과 프롬프트에 절대 전달되지 않는다.
- 인용문·부정문·번호 목차·TODO 완료만으로 후보/저장 항목이 만들어지지 않는다.
- 저장·수정·거절·중복 승인·낡은 revision·존재하지 않는 범위·타 프로젝트 접근을 검증한다.
- 승인 전후 재시작에도 상태가 보존되고 모델 도구가 승인 API를 우회할 수 없다.
- 비활성화/삭제/범위 이동 후 다음 요청에서 전달되지 않으며 캐시에도 잔존하지 않는다.
- 전달 기록은 실제 컨텍스트 payload와 일치한다. 예산 초과 제외 항목을 ‘사용됨’으로 표시하지 않는다.
- 제안 OFF/사용 OFF 각각 독립 동작하며 네트워크·저장 실패 시 성공 표시하지 않는다.
- 실제 모델 시나리오 평가: 지속 선호, 일회성 요청, 사용자 정정, 중복 거절, 민감 정보, 프롬프트 인젝션. 모델 평가는 결정적 저장/권한 테스트와 분리한다.

## 9. 이번 범위 밖
무승인 자동 저장, 다른 계정 간 공유, 외부 서비스 동기화, 임베딩 기반 대규모 장기 기억은 MVP 이후 검토한다. 이번 요청에서는 위 기능을 구현하거나 기존 기억 데이터를 변경하지 않았다.
